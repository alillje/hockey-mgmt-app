# Local POC API contract — v1.4

Backend and frontend agents agreed this contract before implementation. API base: `/api`; camelCase JSON; UUID resource identifiers; ISO 8601 UTC `updatedAt` values. Development frontend proxies requests to `http://localhost:5180`.

## Optional local Supabase Auth

- `GET /api/auth/config` is anonymous and returns `{ "enabled": boolean, "supabaseUrl": string | null, "publishableKey": string | null }`. The URL and publishable key are public browser configuration; no database password or Supabase secret key is returned.
- In local Supabase mode, the frontend requests an email magic link from Supabase Auth and sends `Authorization: Bearer <access-token>` to the hockey API through its shared API client. The backend verifies the token signature against the configured project's asymmetric signing keys, plus issuer, `authenticated` audience, expiry, authenticated role, and a UUID user subject. An optional configured user-ID allowlist further restricts access. Requests without an accepted token return 401.
- `GET /api/health`, `GET /api/readiness`, and `GET /api/auth/config` remain anonymous. All other current controller endpoints require an accepted token when Supabase mode is enabled.
- Without Supabase mode, local SQLite behavior remains as in v1.3. No user or team ownership is added to saved content by this auth slice; staging deployment remains gated until its authorization scope is approved.

## Catalog and health

- `GET /api/health` → `200 { "status": "ok" }`.
- `GET /api/readiness` → `200 { "status": "ready" }` when the database schema is available and SQL migrations are current; otherwise 503 ProblemDetails. This read-only check does not create or migrate tables.
- `GET /api/catalog` → `200 { "categories": [{ "id": "skating", "name": "Skating" }, ...] }`.
- Category IDs: `skating`, `stick-handling`, `passing`, `shooting`, `tactics`, `warm-up`, `other`.

## Drills

- `GET /api/drills?search=&categoryId=&tag=` → array of full drill resources. All filters are optional. Search matches title, notes, or tags; tag matches a complete tag, ignoring case and redundant whitespace.
- `GET /api/drills/{id}` → drill resource or 404.
- `POST /api/drills` → 201 with resource and Location header.
- `PUT /api/drills/{id}` → 200 with updated resource or 404.
- `DELETE /api/drills/{id}` → 204, 404, or 409 if a training references the drill.

Upsert body: `{ title, categoryId, notes, diagram, tags? }`. Resource adds `{ id, updatedAt }` and always includes `tags: string[]`. Titles are required (maximum 120 characters); notes default to empty (maximum 6000 characters). Category must exist and remains for API compatibility; folders use the tags array. The frontend derives the legacy category from the first matching suggested category tag, or `other`.

```typescript
type Point = { x: number; y: number };
type EquipmentType = 'cone' | 'goal' | 'tire' | 'smallTire' | 'player' | 'puck' | 'puckPile';
type PathKind = 'skating' | 'passing' | 'puckHandling';
type Diagram = {
  version: 1;
  objects: Array<{
    id: string;
    type: EquipmentType;
    x: number;
    y: number;
    rotation: number;
    color: string;
    label: string;
  }>;
  paths: Array<{
    id: string;
    kind: PathKind;
    points: Point[];
    color: string;
  }>;
};
```

The full rink uses a 1000 × 500 coordinate system. Positions/points are finite and inside those bounds; rotations are finite; colors are six-digit hex strings. Element IDs are unique UUID strings generated by the client; labels default to empty (maximum 40 characters). Empty diagrams are valid. Limits: 200 objects and 100 paths per diagram; each path requires 2–500 points. Unsupported versions/types and excessive payloads produce 400 validation responses.

`smallTire` is half the linear size of `tire`. `puckPile` renders several pucks but is one saved object, with one position, rotation, and identifier. A red-player creation preset uses the existing `player` type with a red `color`; it does not add another equipment type. Goal rotation controls snap to the next 90° orientation; other equipment retains 45° increments. Existing finite rotations remain valid so opening older diagrams does not change saved data. These additions retain diagram version 1 and require no database schema changes.

## Trainings

- `GET /api/trainings?search=&tag=` → array of full training resources, with optional search/tag filters matching the drill list semantics.
- `GET /api/trainings/{id}` → resource or 404.
- `POST /api/trainings` → 201 with resource and Location header.
- `PUT /api/trainings/{id}` → 200 with updated resource or 404.
- `DELETE /api/trainings/{id}` → 204 or 404.

Upsert body: `{ title, notes, items: [{ drillId, durationMinutes, notes }], tags? }`. Resource adds `{ id, updatedAt }` and always includes `tags: string[]`. Array order is session order; repeated drills are allowed (up to 100 entries). Duration is an integer from 1 to 240 minutes. Titles and notes follow drill limits. Missing drill references produce 400. Empty trainings are valid drafts.

## Tags and compatibility

- Tags are labels from the fixed catalog only: Skating, Stick handling, Passing, Shooting, Tactics, Warm-up, and Other. Creating custom tags is not supported.
- Accept up to 20 supplied entries; trim and collapse whitespace, deduplicate case-insensitively, preserve order, and return canonical catalog spelling. Unknown labels produce 400. There can be at most seven distinct tags after normalization.
- Explicit `[]` means no tags. The UI groups those items under Uncategorized. A tagged item appears in every corresponding folder without being copied.
- Omitted or null tags preserve existing tags on PUT. Legacy drill POST without tags derives a single tag from `categoryId`; training POST defaults to no tags. The current frontend always supplies tags.
- Practice tags are independent from the tags of its drills. Existing practices receive a one-time union of referenced drill tags when upgrading the original schema.
- SQLite schema version 1 adds `TagsJson` columns transactionally and backfills legacy values. Version 2 normalizes and deduplicates the existing tag arrays, mapping unsupported legacy labels to Other. Resource IDs, notes, diagrams, timestamps, and practice entries are preserved. Repeated starts preserve explicit tag edits and empty tag arrays. No table drops or resets are part of the upgrade.

## Errors and POC boundaries

Errors use ASP.NET Core ProblemDetails (`status`, `title`, optional `detail`, and validation `errors`). The local workspace shares one SQLite database and has no per-user ownership or teams yet. Drills referenced by trainings stay live: changing the drill updates its use in existing trainings. PDF export is a client capability and has no API endpoint.
