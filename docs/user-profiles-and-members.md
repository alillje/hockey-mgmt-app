# Profiles and member access

Every signed-in user completes their first and last name before using the workspace, including existing users whose profile has not yet been saved. Account lets them update their name. Names are required and limited to 100 characters each; Unicode, spaces, apostrophes and hyphens are supported. The server uses the authenticated UUID and verified-session email, never submitted identity fields. Profile changes cannot change membership or administrator privileges.

Organisations lists every organisation the current user belongs to, their organisation role, and the teams and roles available to them. Team members can open their own teams' member lists, showing names and team roles. Organisation administrators are listed separately, because their inherited access does not require team membership. An administrator who is also explicitly a team member can appear in both lists. Organisation administrators retain organisation-wide member management and can see saved verified email addresses; ordinary team rosters never return email addresses. Names not yet completed are shown as Profile not completed. Member management still uses stable UUIDs internally.

Profiles are application records in the private hockey schema. They do not use editable Supabase user metadata for authorisation. The profile table follows the application's existing UUID identity convention and is not exposed through the Supabase Data API. RLS and privilege revocation block direct anonymous/authenticated database access; the backend validates profile ownership and current organisation/team memberships even with its privileged connection. Removing membership does not delete the person's reusable profile.

The reviewed EF UserProfiles migration adds an empty table. SQLite creates that table using the existing local upgrade path. Existing authentication, content and memberships are retained. No names are guessed or imported from email addresses. No signup trigger, Supabase template change, dashboard setting, credentials or infrastructure deployment is required.

After merging and successful CI, release to stage using the application workflow, which applies the migration before deploying. Sign in with OTP, complete a profile, edit the name under Account, and compare an administrator and a regular team member's organisation/roster views before promoting to prod. Existing users are prompted on their next app load; no forced logout is required.
